## 发现

### 1. P1：UART5 的完整 18 字节遥控帧无法沿当前回调路径被解析

- `BSP/Src/bsp_uart.c:59` 以 `SBUS_RX_BUF_NUM` 初始化 UART5 双缓冲 DMA；该常量在 `Components/Device/Inc/Remote_Control.h:31` 为 18。
- `bsp_uart.c:77`、`:97` 将 `RxXferSize` 和 NDTR 均设为 18；开启 DBM，但未安装双缓冲传输完成回调、未开启相应 TC 中断。
- 当前随项目编译的 `Drivers/STM32H7xx_HAL_Driver/Src/stm32h7xx_hal_uart.c:2388` 只在 `0 < NDTR < RxXferSize` 时触发 IDLE 接收事件，传入长度为 `RxXferSize - NDTR`，因此只能得到 1～17。
- `bsp_uart.c:131`、`:151` 却只在 `Size == 18` 时调用 `SBUS_TO_RC()`。完整帧完成时 DBM 自动切换内存并重新装载计数，IDLE 分支不会补发完整帧事件。

影响：正常的直连 DT7 18 字节帧无法更新遥控状态。USART1 使用相同初始化方式，满缓冲帧也需检查。`APP/Compat/app_can.c` 另有 FDCAN2 双板遥控备用输入，本发现不等于该备用链路也不可用；没有备用输入时，PC 模式选择也会受到影响。

修复：选择一种完整接收模型，正确实现 DMA 完成事件与已完成缓冲区选择，或采用容量大于单帧的接收缓冲及流式解析。不能直接把 NDTR 改成两个缓冲的总长，否则会越过单个内存区的容量。

验证：回放连续完整 18 字节帧、短帧、帧间空闲和连续满缓冲数据，核对解码计数与数据内容；同时验证遥控来源切换。

### 2. P1：夹爪标零重复发布旧时间戳，约 100 ms 后力矩被输出层撤掉

- `APP/Arm_L_task.c:423` 已有首次 `Arm_PrepareAndPublish()`，所以当前版本并不是“力矩从未发布”。
- 但循环 `:425` 调用的 `Arm_PublishCurrent()`（`:302`）只重新复制旧快照，不更新 `tick_ms`。
- `APP/Moter_task.c:230` 在命令年龄超过 100 ms 时改发零 Kp、Kd 和力矩，而标零循环允许持续最多 12 s。
- `Arm_L_task.c:433`、`:437`、`:439` 用“移动过后连续静止”判断机械止点，没有区分被撤掉驱动力造成的停止。

影响：可能只运动很短时间后停止，继而把中途位置误当止点保存；也可能因移动不足而初始化失败。具体机械结果依赖负载和摩擦，但超时撤力矩的代码路径是确定的。

修复：标零状态每拍验证反馈和故障后构造新命令，正常刷新时间戳；确认实际仍施加标零力矩再累计静止样本。不要在输出任务中无条件刷新时间戳，以免掩盖控制任务卡死。补充标零行程、受阻和超时判据。

验证：让模拟或台架夹爪在超过 100 ms 后仍运动，确认持续受控驱动；分别覆盖正常止点、初始已在止点、反馈中断、途中受阻和未达到最小位移。

### 3. P1：回零循环没有发布新目标，并仅凭规划值置 READY

- `APP/Arm_L_task.c:545`、`:546` 初始化斜坡和增益。
- `:558`～`:582` 每拍更新并限制 `ArmData` 中的新目标。
- `:595` 仍调用 `Arm_PublishCurrent()`，未将本拍目标和增益复制进输出快照；循环中实际发布的是旧命令。
- `:585` 的完成条件比较斜坡输出与目标，不比较电机实测位置。
- 退出循环后 `:602` 才构造新快照，随后 `:605` 置 `Arm_L_Ready=1`。

影响：只要起始位置不等于目标，内部规划可“走完”而电机未收到中间轨迹，最后一次性收到终点和增益。READY 不能证明机械臂到位。前面的重新标零可能让部分轴恰好处于数值零，从而掩盖此问题。

修复：每拍构造并发布新快照；完成条件增加全部关节新鲜反馈、位置误差阈值、速度阈值和连续稳定时间。目标轨迹结束与物理到位应分开表示。

验证：从非零反馈位置启动，检查每一拍实际 CAN 目标连续变化；模拟电机不跟随时不能置 READY，必须到达超时或故障处理。

### 4. P1／取决于标定要求：普通上电无条件重写 J1～J6 零点

- `APP/Arm_L_task.c:507` 每次启动调用 `Arm_SaveMotorZero()`。
- `:126`～`:131` 给 1～6 号电机发送保存零点命令，没有用户标定步骤或机械姿态检查。
- `APP/DM_motor.c:149` 的保存零点函数发送 `FF FF FF FF FF FF FF FE`，没有返回成功状态供调用方判断。
- 后续 `Arm_WaitMotorFeedback()`（`Arm_L_task.c:161`）只要求反馈年龄不超过 100 ms，没有要求每轴反馈一定产生于零点命令之后、也没有确认零点生效。

影响：如果要求保留固定机械零位，则任意上电姿态都会被重新定义为零，软件限位、预设姿态和上位机坐标的机械意义随之改变。如果设计明确要求每次人工摆到固定姿态后标零，应把这一前提写入流程并验证，而不是默默执行。零点命令是否写入非易失存储还需以具体电机型号资料为准。

修复：分离首次/维护标定与普通启动；普通启动读取并验证已有坐标，显式标定时逐轴检查发送结果及命令后的新反馈。

### 5. P1：遥控触发故障重试的条件不可达

- `APP/Arm_L_task.c:331` 检测模式变化后，`:347` 已执行 `prev_ArmMode = ArmData.ArmMode`。
- 随后的 `:381` 却要求当前为 `ARM_POWERLESS` 且前一模式不是 `ARM_POWERLESS`。这时前一模式变量已经等于当前模式，因此不会调用 `Arm_Output_RequestRetry()`。
- `APP/Moter_task.c:271`～`:283` 依赖重试请求才能解除 `bus_inhibit` 并重启失败关节。

影响：发生相关电机掉线或总线恢复抑制后，预期的拨杆重试操作无法触发。现有控制测试直接调用重试函数，不能验证上层拨杆是否真的产生请求。

修复：在更新历史模式前保存/处理切换沿；把操作者选择的模式与故障强制进入的 POWERLESS 分开。否则故障强制切换也可能被误当作人工重试。启动失败是否必须复位应另行明确，不应顺手自动解除。

验证：经真实模式入口模拟拨杆切换，覆盖正常切换、故障强制无力、操作者主动确认重试及持续保持拨杆，确认不会自动重复重试。

### 6. P2：自定义控制器输入尚未接通，J5/J6 字段也不一致

- `APP/Compat/app_uart.c:9` 仅定义零填充的 `uart1_rx_process_buf`；注释明确说明此测试构建的可选 UART 链路是占位实现。没有找到给它写入接收数据的路径。

- CAN 自定义控制器解码写的是 `CC_data`，没有连接到上述 `Custom_RC` 读取路径。

影响：如果设计包含自定义控制器控制 J5/J6，目前不能按这条数据链实现；若本测试构建主动关闭此功能，应明确列为不支持。

修复：确定实际输入接口、统一字段类型和单位，建立明确的数据更新与超时规则，再删除占位或重复路径。

### 7. P2：标准验证入口失败，且关键控制流程没有自动化覆盖

修复：修正未使用参数与路径筛选，让标准入口恢复可运行；增加实际启动、模式切换和 UART 事件链的行为测试。文档中的“已修复”或文本匹配测试不能作为验收证据。

| 自定义控制器 J5/J6 跟随 | 输入链路和字段未接通 |
| 预设动作 | 有实现；完整动作正确性还受零点、限位、模式入口影响。`TAKE_WATER` 原拨杆入口已被 PC 模式替代，是否符合需求需确认 |

USB 初始化实际由 MCU 初始化路径调用；没有把“INS 任务被禁用”当成 USB 未初始化。当前已有命令有效期、反馈新鲜度、会话撤防和输出超时等保护；主要问题在于这些模块之间的调用和状态衔接。

## 后续优化顺序

1. **先恢复正确性**：修复 UART 接收和快照发布；分离标定与普通启动；以实测到位判断 READY；修复人工重试切换沿。保留已有输出超时保护。
2. **将启动改为非阻塞状态机**：上电等待、使能、标定、回零、就绪、故障各自有进入条件、超时和退出动作，统一处理撤力、反馈失效及诊断。避免长阻塞循环维护另一套发布规则。
3. **统一关节配置与坐标**：把 ID、方向、零偏、单位、限位、默认增益及运动约束集中管理；预设目标必须落在同一配置的范围内。夹爪电机角度与 ROS 直线位移明确转换。
4. **完善运动约束**：按实际周期计算速度/加速度约束，评估独立关节限速对多轴同步轨迹的影响；为 PC 控制明确自碰撞和工作空间限制的责任。仅有限位不能证明整机无碰撞。
5. **补齐可观察性与回归测试**：公开启动阶段、失败原因、快照年龄、标零结果、重试来源、遥控输入源；把上述失败场景和断链/恢复测试纳入固定验证入口。
6. **最后做维护性优化**：清理失效路径和占位实现，统一注释编码，修正与源码不一致的说明，减少重复的逐轴代码。没有测量依据前，不优先靠省略快照更新来节约计算。

建议验收顺序：主机行为测试 → UART/CAN 帧回放 → 输出隔离检查实际目标帧 → 受控低速单轴台架 → 多轴与上位机轨迹联调。每步都应核对实际输出与反馈，而不是只观察编译成功或 READY 标志。
